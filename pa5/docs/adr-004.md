# ADR-004 — Header-carried correlation id, file-backed idempotency, and return-exchange replay

**Status:** accepted
**Date:** 2026-10-06

## Context

An order has to reach payment, inventory and notification independently, and any of them can be down for a few seconds without the order being lost. That forced four decisions: where the correlation id travels, how many times a failing message is retried, how notification-service avoids notifying twice when delivery is at-least-once, and how a dead-lettered message gets back to the one consumer that failed it.

The canonical order schema has `additionalProperties: false`, so the correlation id cannot be a field on the order body. It had to travel outside the body.

## Decision

**Correlation id.** order-service generates `crypto.randomUUID()` in `POST /orders` and publishes the order unchanged with `headers: { correlationId }` and `persistent: true`. It is the custom entry in `properties.headers`, not AMQP's own `properties.correlationId`. All three consumers read `msg.properties.headers["correlationId"]` and copy it onto their result events and onto the DLQ and invalid publishes, so one order can be traced across three services' logs.

**Retry.** I kept the scaffold's path: `MAX_RETRIES` of 3 attempts, a failed attempt is `nack(msg, false, false)` so it goes through the provided retry queue, and on the third failure the message is published to `orders.dlq.exchange` with an `originQueue` header and acked. I did not use `requeue=true`.

**Permanent vs temporary.** Each consumer parses the body inside its `try`. A `PermanentError` is thrown for: body is not valid JSON, body is not a JSON object, no string `orderId`, and no `correlationId` header. These go to `orders.invalid.exchange` with the original bytes and headers, are acked, and are never retried. Only the simulated failure is temporary.

**Idempotency.** notification-service keys on `correlationId`, which is a business key because it handles one message per order. `loadProcessed()` re-reads `/data/processed-ids.json` on every message, so the file is the single source of truth. `saveProcessed()` writes a temp file and renames it, so a crash cannot leave a half-written file. The order of operations is: check the set, append the line to `notification.log`, add the id, save, publish the result, ack.

**Replay.** `POST /dlq/replay` takes messages one at a time with `channel.get("orders.dlq")` and republishes the original bytes to `orders.return.exchange`, using the `originQueue` header as the routing key, so only the failing consumer sees it. Headers go through `withoutRetryHistory`, which drops `x-death` so the message gets a fresh three attempts. Each message is acked only after it has been republished. A message with no `originQueue` is put back and the loop stops, rather than guessing a destination.

## Alternatives considered

- **AMQP's `properties.correlationId`** instead of a custom header. It would work, but the spec and the course tooling use `headers.correlationId`, and the two are easy to confuse. I stayed with the header and read it in one place per service.
- **An in-memory `Set`** for idempotency. It passes a test where nothing restarts, but after `docker compose restart notification-service` it forgets every order and would log a replayed or re-published order again. That is exactly the case the idempotency requirement exists for.
- **Saving the id before writing the log line.** That swaps the failure mode: a crash in between would mean an order that is never logged instead of one logged twice. I judged a duplicate notification the lesser harm.
- **`requeue=true` on failure.** It skips the retry delay and can loop with no `x-death` ever appearing, so the retry count never advances.
- **The naive retry topology** where retry queues dead-letter back to the fanout. A retry for payment would be redelivered to inventory and notification too. The per-queue return exchange avoids that, and the idempotency requirement stays anyway.

## Consequences

**Easier:** a failing consumer is isolated; a bad message is diagnosed immediately in `orders.invalid` instead of after three pointless retries; a replay cannot cause a second inventory run.

**Harder, and what breaks first:**
- **Header-only correlation.** A future consumer that forwards a message without copying the header silently breaks tracing, and nothing enforces it.
- **A crash between the log append and the id save** means one duplicate log line on redelivery. Accepted, as above.
- **Two replicas of notification-service** would race on the file: both read, both add an id, and the last write wins, so an id can be lost and an order notified twice. The file is fine for one instance only.
- **Payment succeeds but inventory is down longer than three retry cycles:** the order sits in the DLQ and nothing downstream is told. There is no compensation, so payment has already happened. A human has to notice and replay.
- **Order state in order-service is in memory,** so `GET /orders/:id` loses everything on restart.
- **The ids file grows without bound.** It is re-read on every message, so cost rises with the number of orders.
- **A DLQ message with no `originQueue`** blocks the replay loop behind it until someone handles it.
