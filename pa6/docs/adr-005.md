# ADR-005 — Contract-first checkout with a sequential, compensating saga orchestrator

**Status:** accepted
**Date:** 2026-10-30

## Context

POST /checkout needs to take a single canonical order and coordinate four downstream services (payment, inventory, shipping, and notification) that are outside my control, while still keeping the overall process consistent when something goes wrong. That turned out to be more complicated than it first appeared.

The first challenge is that only two of the four steps can be reversed. The provided mocks expose /payment/refund and /inventory/release, but there are no equivalent rollback endpoints for shipping or notification. This means that if shipping fails, the orchestrator can release inventory and refund payment. However, if notification fails after shipping succeeds, the shipment remains in place because there is no way to cancel it. The saga is therefore intentionally only partially reversible.

The second challenge is preventing duplicate charges when the same request is retried. The Idempotency-Key header must support three different outcomes: replaying a previously stored result, returning 409 idempotency_payload_mismatch when the request body differs, and returning 409 idempotency_conflict when the original request is still being processed. Since the scaffold tracks new requests as in_progress, duplicate requests arriving during saga execution needed an explicit response rather than waiting indefinitely.

The third challenge came from starting with the API contract. Writing openapi.yaml first and validating it with Spectral forced several decisions that would otherwise have remained ambiguous. I had to define a concrete maximum size for the items array (25), create schemas for every 4xx and 5xx response, and specify exactly which error codes could appear in each state. Because the canonical order schema does not define maxItems, I could not reuse it directly and instead had to restate the order structure within the contract.

## Decision

I adopted a contract-first approach. The OpenAPI specification (openapi.yaml) was written and linted successfully with Spectral before making any changes under orchestrator/src/. The contract restates the canonical order schema and adds maxItems: 25 to the items array.

The 25-item limit reflects a typical consumer checkout scenario, where baskets remain relatively small. A hard upper bound also keeps each saga predictable and inexpensive to execute or retry. The contract additionally limits the trace to six entries, which covers the four forward-processing steps and up to two compensations.

In orchestrator/src/server.ts:

- handleCheckout validates both the request header and canonical order schema, then separately enforces the 25-item limit through MAX_ITEMS, since the canonical validator is unaware of that constraint.
- toCents and fromCents calculate payment values using integer cents only and format the final amount as a two-decimal-place string. Floating-point arithmetic is never used.
- callDownstream performs each outbound request using an AbortController connected to REQUEST_TIMEOUT_MS. If the request is aborted, it is treated as a timeout (trace.status = timeout, saga code timeout, HTTP 504). Any other non-success response is treated as a business failure (trace.status = failed, HTTP 422) and uses the downstream error code extracted by extractErrorCode.
- The saga executes each step sequentially using a simple for loop with await. If any step fails, previously completed steps are compensated in reverse order, but only when a compensation endpoint exists (payment and inventory). If a compensation itself fails, the orchestrator still attempts all remaining compensations and returns 422 with status failed and code compensation_failed.
- The saga status becomes compensated when one or more completed steps are successfully rolled back after a later failure. If payment itself fails or times out, the saga status remains failed, because there is nothing to compensate.
- For idempotency, a key is checked and marked as in_progress without any asynchronous gap between the read and write operations. Within a single Node.js process, this prevents two requests from claiming the same key simultaneously. Completed requests replay the exact stored HTTP status and response body. persistAndRespond writes the saga record first and the idempotency record second, both under /data, ensuring successful replays even after a container restart.

After the implementation was complete, I updated the contract to reflect the actual behaviour. A message field was added to the saga result, and unitPrice was restricted to non-negative values because the code already rejects negative prices and the API contract should not promise behaviour that the implementation does not support.

## Alternatives considered

Another option was executing downstream calls in parallel to reduce overall latency. While attractive from a performance perspective, the checkout process is inherently sequential because each step depends on the success of the previous one. Parallel execution would also complicate failure handling by introducing multiple in-flight operations that might require unwinding. A strictly sequential workflow is easier to reason about and aligns with the timestamp-based tests.

I also considered using choreography, similar to the approach implemented in PA5. For checkout, however, orchestration was the better fit. The business requirement is to return a single authoritative outcome (completed, compensated, or failed) and apply compensation in a clearly defined order. Event-driven choreography offers stronger decoupling and scalability, but no single component owns the final outcome. That would remove the ability to provide a definitive synchronous response to the caller.

Validation could also have been generated directly from the OpenAPI definition instead of enforcing the item limit separately in code. That approach would reduce the risk of contract and implementation drift. I chose a manual validation check because it was simpler to implement, although it does leave open the possibility that the contract and code diverge over time, which is precisely the type of mismatch targeted by manual review.

A cleaner design would have provided compensation endpoints for both shipping and notification, making the saga fully reversible. However, the mock services are fixed and replaced during grading, so that option was not available. Given the system constraints, the most accurate behaviour is to roll back only the services that expose compensating actions and acknowledge that a shipment created before a notification failure cannot be undone.

## Consequences

One benefit of this design is transparency. The API contract and execution trace make each checkout easy to inspect and audit. Extending the saga with a fifth step is straightforward: add another entry to the step sequence, update the trace limit, and extend the corresponding step enumeration in openapi.yaml.

The design also comes with several accepted limitations:

- If the orchestrator crashes while a saga is running, the associated idempotency key remains marked as in_progress. Any later request using that key will continue to receive idempotency_conflict, and any successful payment authorization may never be refunded. A staleness timeout or recovery process could solve this, but neither was implemented.
- When payment times out, the saga assumes the operation never completed and therefore performs no compensation. However, the payment service may actually have processed the request successfully. If REQUEST_TIMEOUT_MS is configured too aggressively, this could leave behind an authorised payment that is never refunded.
- Requests using different idempotency keys but the same orderId are not coordinated. Both sagas can execute independently, and because the saga store is keyed by orderId, the later execution will overwrite the earlier record.
- In-flight idempotency protection relies on a single Node.js instance and synchronous file operations. The approach would fail in a multi-instance deployment and would require a shared persistence layer or distributed lock to remain correct.
- The 25-item limit and validation against negative prices are enforced by the implementation but are not covered by any public test cases. I also did not perform dedicated manual tests for those scenarios.
