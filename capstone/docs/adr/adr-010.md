# ADR-010 — Stuck sagas: detect by owner, never resume, compensate on operator command

**Status:** accepted
**Date:** 2026-11-20

## Context

The orchestrator calls four providers one after another. If it is killed in the middle, the saga store says `processing` with some steps recorded, but the call in flight is unknown. When I killed the orchestrator while shipping was delayed by 5 s, the mocks showed one charge, one reservation and a shipment: the carrier finished the call it was given, though no process was left to record the answer. After the restart, the saga store had no outcome for that order, and the unacked `order.accepted` message came back from `saga.queue`.

So a crash leaves the saga in an unknown state: the store says one thing, the providers may have done more. Running the saga again could charge or reserve twice, or ship twice, because shipping has no idempotency key.

## Decision

**Detection rule.** At every start the orchestrator draws a new `runId` (a UUID) and stores it in each saga it starts, in the `owner` field of `saga-store.json` (`<orchestrator/src/store.ts>`). A saga is stuck when its state is `processing`, it has no outcome, and its `owner` is not the current `runId`. That means "its steps were running under a run that no longer exists". `<describe your timing: e.g. the scan runs at start, and within SAGA_STUCK_AFTER_MS>`.

A stuck saga becomes `needs_attention`. The orchestrator publishes `order.needs_attention` and writes a `saga.stuck` hop. When the redelivered message arrives, the same `correlationId` with an `owner` from another run means stuck, so no step runs and the message is acked (R-4.2.5, R-4.7.2).

**Operator compensation.** `POST /sagas/:cid/compensate` runs, in reverse order, the compensations of completed steps that are not yet compensated: `inventory_release`, then `payment_refund` for standard and express orders, and `inventory_release` only for b2b. Shipping and notification have no compensation. The keys are `release:<businessKey>` and `refund:<businessKey>`, so a repeat is harmless at the provider. The saga ends `compensated` with the code `operator_compensated`. If a compensation fails, it ends `compensation_failed`, and a later call runs only the compensations that have not yet succeeded. A repeat call on a finished one returns the same answer (R-4.7.8). A call while one is running returns 409 `compensation_in_progress`, guarded by `<in-memory lock or persisted flag>`.

## Alternatives considered

- **Resume automatically from the last recorded step.** It would need to know whether the call in flight had an effect. Payment and inventory could be asked again with the same key, but shipping and notification have no key, so a resume could create a second shipment or notice. It would also hide the crash from the operator. Rejected.
- **Re-run the whole saga from the start.** Provider keys would make payment and inventory safe, but shipping would be duplicated. Rejected for the same reason.
- **Detect by timeout (a saga `processing` for longer than N seconds).** It needs no run id, but a slow saga would be flagged while it is still running, and a crashed one would wait for the timeout. Rejected as less exact, though it is simpler.
- **Compensate automatically after the crash.** It would reverse an order that might have finished its last step before the crash. It is safer to let a person look first.

## Consequences

**False positives.** The rule can flag a saga that was actually fine: one that finished its last step just before the crash but did not persist the outcome, or one whose provider calls all succeeded. Compensating it undoes a good order. The rule also cannot tell a crash at step 1 (nothing happened) from one at step 4 (everything happened).

**What the operator must check before pressing compensate.** Look at `GET /trace/:cid` and each provider's `/admin/effects` (or the real provider) to see which effects really happened. Compensation only covers payment and inventory. A shipment that already exists is not cancelled, and a notice already sent is not recalled. The operator must handle those by hand, for example by contacting the carrier. The compensation is only as good as the record of completed steps, so a step that finished but was not recorded will not be undone.

**Compensation matrix.** standard and express: shipping failure runs `inventory_release` then `payment_refund`. b2b: only `inventory_release`, because there is no payment. A payment 4xx or a b2b inventory 4xx needs no compensation.

**Costs.** A needs_attention order waits for a human, so completion is delayed and the alert `stuck_sagas` must be watched. The `owner` check relies on the store surviving the crash, so the atomic write in `saga-store.json` matters.

**What Temporal changes.** The workflow's history is durable, and Temporal resumes the workflow on a worker after a crash. The activity retries and the provider keys make the repeat safe. So in temporal mode there are no stuck sagas: `GET /sagas/stuck` answers `{sagas: []}` and compensate returns 409 `saga_not_stuck`. The problem of non-idempotent shipping remains, but the engine tracks which activities finished, so a completed activity is not run twice.
