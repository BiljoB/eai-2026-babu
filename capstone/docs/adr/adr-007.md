# ADR-007 — Starting the saga from an event on saga.queue

**Status:** accepted
**Date:** 2026-11-20

## Context

In PA6 the saga started from an HTTP request. The caller waited for the whole saga, so a slow provider held the caller's connection open. If the orchestrator was down, the order was lost unless the client retried. There was no queue between acceptance and processing, so a burst of orders had nowhere to wait. Retries, dead-lettering and a replay path did not exist for the saga's own start.

In the capstone, intake must answer `202` quickly and independently of the providers. The saga needs a durable start that survives an orchestrator restart, and it needs a redelivery path when a crash happens between persisting an outcome and publishing it (R-4.2.4).

## Decision

Intake publishes `order.accepted` to `orders.exchange` (persistent, publisher-confirmed) and answers 202 only after the broker confirms. The orchestrator consumes `saga.queue` (`<orchestrator/src/consumer.ts>`).

*Ack timing.* The consumer persists the saga's new state together with its outcome event in `saga-store.json` (atomic rename), then publishes the outcome to `orders.outcome`, then acks. Messages for a first-step temporary failure (payment, or inventory for b2b) are nacked into the retry path until `MAX_RETRIES`. After that the message goes to `orders.dlq.exchange` and is acked, and the saga is `parked`.

*Crash after persisting but before publishing.* The message is still unacked, so the broker redelivers it. The consumer sees the same `correlationId` with a stored outcome and republishes that stored envelope with a new `messageId`, then acks. No step runs again (R-4.2.4, R-4.2.6). The cost is that outcome events are at-least-once, so every consumer of `orders.outcome` must tolerate duplicates. The notifier dedupes on `correlationId`, and intake ignores any event that is not an allowed state move.

*Prefetch and concurrency.* Prefetch is `<N, at least SAGA_CONCURRENCY>`, and an in-process limiter allows `SAGA_CONCURRENCY` (5) sagas at once. If prefetch were lower than the limit, the limit would never be reached. If it were much higher, messages would sit unacked in this consumer while other consumers or a restarted instance could have taken them. Steps inside one saga run sequentially.

*How GET /orders learns the state.*Intake subscribes to `orders.outcome` (`#`) through its own queue (`<queue name>`). It applies each event to `orders.json` only if the move is allowed by the state table (R-4.4.4 to R-4.4.10). Late or duplicate events are ignored. The state ranks forward only: a terminal state never changes, and `accepted` can move to anything. That is why a late `order.processing` cannot undo `completed`.

## Alternatives considered

- *HTTP from intake to the orchestrator.* Simple to follow, but intake would be coupled to the orchestrator's availability and latency, and a crash would lose the order. It would also need its own retry and DLQ logic, which RabbitMQ already provides.
- *Ack before running the saga (at-most-once).* It avoids redelivery, but a crash mid-saga loses the order silently. I rejected it because losing a paid order is worse than handling a duplicate.
- *A real transactional outbox.* It would make state and publish atomic, but needs a relay process and more store code. With one orchestrator and a file store, persist-then-publish-then-ack plus republish on redelivery gives the same at-least-once guarantee for far less code.
- *Intake polling the orchestrator for state.* It adds load and delay against the 2 s requirement (R-4.4.11). Event subscription is faster and uses what exists.

## Consequences

*Easier.* Intake stays fast and independent of the providers. Retry, DLQ and replay come from the broker topology. A crashed orchestrator picks its work up again from the queue.

*Harder, accepted costs.*
- Outcome events can be delivered more than once, so every consumer needs dedupe or state-machine guards.
- Intake's `GET /orders` is eventually consistent, within 2 s, not synchronous with the saga.
- If the orchestrator dies mid-step, the saga cannot be resumed safely, and it becomes `needs_attention` (ADR-010).
- A single JSON file store limits throughput. Every write rewrites the whole file, which I accept at this scale.

*What breaks first.* Under heavy load, the whole-file rewrite in `saga-store.json` becomes the bottleneck before the broker or the providers do. With the file store, running a second orchestrator instance would be unsafe.
