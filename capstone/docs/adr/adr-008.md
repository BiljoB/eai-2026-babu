# ADR-008 — Three dedup layers: client key, business key, provider keys

**Status:** accepted
**Date:** 2026-11-20
            
## Context

One order can turn into two in several places:

- The client retries `POST /orders` after a timeout or a lost response.
- The client submits the same logical order again with a new key.
- RabbitMQ redelivers `order.accepted` after a crash or an unacked message, or an operator replays a DLQ entry.
- The saga's first-step call is repeated in the retry path after a timeout, when the provider may already have charged or reserved.
- Outcome events are at-least-once, so the notifier may see one twice.

No single mechanism covers all of these, because each repeat happens at a different boundary and carries different identifiers.

## Decision

*Layer 1: the intake Idempotency-Key.* Intake stores `key → {bodySha256, state, response, correlationId}` in `/data/idempotency-store.json` (`<intake/src/idempotency.ts>`). The record is kept until `down -v`, with no expiry. The same key and the same bytes returns the stored status and the same `correlationId`, with no new publish. The same key with a different body gives 409 `idempotency_payload_mismatch`. A request still in flight gives 409 `idempotency_conflict`.
*Only this layer catches:* a client that retries a POST whose 202 was lost. Without it, each retry would get a new `correlationId` and publish a second event, and the saga would see them as different orders.

*Layer 2: the saga business key.* The orchestrator keeps `businessKeys: businessKey → correlationId` in `saga-store.json` (`<orchestrator/src/store.ts>`). The same `businessKey` under a different `correlationId` is recorded as `duplicate` with `duplicateOf`, and no step runs. The same `correlationId` with a stored outcome is a redelivery, and the stored outcome is republished.
*Only this layer catches:* the same logical order submitted again with a new Idempotency-Key (failure scenario 9). Layer 1 sees a new key and accepts it, and layer 3 would see the same `authorize:<businessKey>`, but it must never be reached, because the duplicate saga would otherwise also reserve and ship.

*Layer 3: the provider keys.*Calls to payment and inventory carry `authorize:`, `refund:`, `reserve:` and `release:` plus the `businessKey` as the Idempotency-Key. The mock stores the answer and returns it again without a new effect.
*Only this layer catches:* the first-step retry after a timeout or `effectThenFail`. The provider charged, our call failed, and the retry repeats the call. Layers 1 and 2 cannot know whether the charge happened, and only the provider can answer that.

*Notices.* The notifier dedupes on `correlationId` in `/data/processed-ids.json`, checking before the send and recording after a successful send. The notification provider has no idempotency key, so there is a window: if the send succeeded but the call timed out, a retry sends a second notice.

## Alternatives considered

- *One layer only (provider keys).* It stops double charges, but a resubmission would still run a full second saga: reservation, shipping and a second customer notice, each with a different effect. Rejected.
- *Dedupe on `correlationId` only.*It is useless for a resubmission, because each accepted submission gets a new `correlationId` by design (R-3.3.1).
- *An idempotency key on the notification call.* Not possible: the provider offers none, and I do not control it. I could record "intent to send" before the call, but then a crash between the record and the send would lose the notice entirely, which is worse than a duplicate.
- *Expiring the intake key after some hours.* It would limit store growth, but a late retry would then create a new order. I kept the keys forever, at the cost of a growing file.

## Consequences

*Why notices are at-least-once and charges exactly-once in effect.* A duplicate charge moves the customer's money twice and is hard to undo. A duplicate notice is a repeated message, and it is harmless. Missing a notice means the customer is never told about a failed order, which is the failure the notifier exists to prevent. So I accept a possible duplicate in order to never lose one.

*The re-order after a decline.* Business-key dedupe is keyed on `${source}:${orderId}`. A customer who retries with the *same* `orderId` after a decline gets `duplicate`, and nothing runs, even though the first order failed. The customer must submit with a new `orderId`. This is correct for retries and surprising for people, and the client system must generate a fresh `orderId` for a genuine re-order.

*Costs.* Both stores are whole-file JSON that grows without limit, and every write rewrites the file. The dedupe check and the state write in the orchestrator must be atomic under concurrency (R-4.10.3), or two sagas for one business key could slip through. The layers do not cover a lost notice in the window between a successful send and the write to `processed-ids.json`, which can produce one extra notice on restart.
