# ADR-003 — Transformation to the Canonical Order Model


**Status:** accepted
**Date:** 2026-09-29

## Context

The main challenge in this assignment was that all three source systems described the same order in different ways.
The web source provided normal JSON data, the mobile source used a different JSON structure with shortened field names and Unix timestamps, and the B2B source sent XML encoded in CP1257. Even something as simple as a product ID was inconsistent. The web system used values like PROD-001, the mobile system only sent 001, and the B2B system used SKU-PROD-001.
One issue that caused problems was the B2B file. It contained a UnitListPrice field that looked like the correct item price, but according to the requirements it could not be trusted. The real price, tax rate, currency, and even product validity had to come from the pricing service instead. That meant the transformation process depended on another system that could return missing products or API errors.
Another complication was that some fields from the source systems were not allowed in the canonical model. Payment-related information existed in the input but had to be removed completely. The canonical model also required prices to be stored as decimal strings with exactly two decimal places, so values could not simply be copied across without formatting.

## Decision

I implemented a separate translator for each source system: translateWeb, translateMobile, and translateB2B.
Each translator is responsible for handling the differences in its own source format and converting the data into one common canonical order structure. This keeps the source-specific logic separated and makes the output consistent regardless of where the order came from.
Before performing a pricing lookup, product identifiers are normalized into the same format. Mobile product IDs receive the PROD- prefix, while B2B product IDs have the SKU- prefix removed. After normalization, the pricing service is used as the single source of truth for item pricing, currency, and tax information.
Prices are formatted using toFixed(2) so the canonical model always receives values like "4.50" instead of "4.5". If the pricing service returns a 404 error, an UNKNOWN_PRODUCT warning is generated. Other pricing failures become PRICING_API_ERROR warnings. In both cases, the problematic item is skipped rather than assigning a price that may be wrong.
For the B2B source, the XML file is decoded as windows-1257 before parsing. The translator also supports both a single LineItem object and multiple LineItem objects because the XML structure varies depending on the number of products in the order. Payment information is intentionally excluded from the canonical object.

## Alternatives considered

One option was to use the prices that already existed in the source files, especially the B2B UnitListPrice. I rejected that approach because the requirements clearly state that those values are not authoritative. Using them would risk producing different results depending on which source the order came from.
Another possibility was to reject an entire order whenever one item failed the pricing lookup. I decided against this because it would cause valid items to be lost unnecessarily. Instead, failed items generate warnings while valid items continue through the transformation process. The downside is that the final order may contain fewer items than the original source order.
I also considered representing prices as integer cents internally. That is a common approach for financial systems, but the canonical schema explicitly requires decimal strings with two decimal places, so it would only add extra conversion steps without providing any real benefit for this assignment.
For XML processing, writing a custom parser was another option. I chose fast-xml-parser because it significantly reduced complexity and allowed me to focus on the transformation logic rather than XML parsing edge cases.

## Consequences

The biggest benefit of this approach is consistency. The rest of the system only has to deal with one canonical order format, regardless of whether the data originated from the web, mobile, or B2B system. Source-specific differences remain isolated inside their translators. The main trade-off is that the transformation now depends on the pricing service. If that service is unavailable, some items may not be enriched correctly and warnings must be handled by downstream systems.
There is also a maintenance cost. If the canonical schema changes, all translators may need to be updated. Similarly, onboarding a new source system would require creating another translator and defining its normalization rules.
If this were a production system expected to run for many years, I would further separate parsing, normalization, enrichment, and validation into independent steps. I would also add stronger runtime validation, monitoring, retry logic for temporary pricing-service failures, and potentially caching for frequently requested pricing data to reduce the number of API calls.
