## Context

 Two encodings inside the same integration, with nothing in either file declaring which is which where the order export is fixed width CP1257 text and the customer is UTF-8 CSV.By reading the order file with plain plain UTF-8 decoder does not throw an error it replaces the non-ASCII bytes, so the name like Bērziņš comes out as B?rzi?? while every fixed width column stays numerically correct. We have to check it where the corruption is invisible.
The amount field is padded to 12 characters and uses a comma as the decimal separator, for example "45,20". And if you convert the value using Number(), Javascript treats it as a plain number and dropping any trailing zero that isn't mathematically significant - so "7800,00" turns into 7800 while no errors are forming.

## Decision

decodeOrderFile reads the order file as raw bytes and decodes them with new TextDecoder("windows-1257"). parseCustomers reads the CSV directly as UTF-8 text.
toIsoDate and toDecimalString are both string transformations where toIsoDate splits DD.MM.YYYY on "." and remake it as YYYY-MM-DD and toDecimalString replaces the comma with a period and returns a string.
In ingest any line whose length is not exactly 77 characters is pushed to rejected with it's 1-based line number, the raw decoded line, and a reason string , then skipped - it never changes the field. This keeps the record from crashing the run or disappearing , every input line ends up in either orders or rejected.

## Alternatives considered

 iconv-lite instead of TextDecoder. Rejected because it adds a dependency for something the platform already does where TextDecoder supports the "windows-1257" and a public tests enforces zero runtime dependencies.
Storing amount as a number and formatting on output. Rejected because the floating point is where exactly trailing zero and precision loss happen. keeping it a string end to end means the value is never at risk and at the cost of not being able to do arithmetic on it directly without an explicit parse the step later.
Asking the upstream system for JSON instead of parsing this at all. This is the alternative most worth taking seriously for a system run over five years. A JSON or declared UTF 8 export would remove the encoding column position fragility entirely and it isn't implemented here because I don't control the upstream system but it is a real long lived integration. 

## Consequences

 What is now easier is adding a new field to the end of the fixed-width layout and telling the malformed input apart from valid-but unusual input like refunds, since rejection is driven by the line length rather than by field content.
What is now harder is the solution is more tightly coupled to the fixed width file format. Any change to the record layout requires updating the field positions in ORDER_LAYOUT and retesting the parser. 
What breaks first is the fixed width parsing logic breaks first because it assumes specific start and end positions for every field. Once those positions change the field such as customer name date amount or currency may be extracted incorrectly.

If a new field is inserted in the middle of the fixed-width record, all field positions after that point shift. Since the parser relies on exact column positions it will start reading incorrect values from the wrong locations. The program may continue running but the data produced will be incorrect.

The fixed-width format only allocates 32 characters for customerName. A longer name will be either be cropped by the exporting system or cause the record length to exceed 77 characters resulting in the record being rejected as malformed.

When someone sends the field as UTF-* by accident the parser always decodes the order file as windows-1257 and if a UTF-8 file is received instead , special characters may be decoded incorrectly producing corrupted customer names and other field texts. The ingestion may still run successfully but the resulting data may be inaccurate.

The cost I accepted is the maintaining a strict fixed-width parser. This implementation is simple and dependency free, but it is fragile when the upstream file format changes.
