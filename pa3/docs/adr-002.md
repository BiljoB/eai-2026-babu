# ADR-002 — Correlation, timeout, and deduplication strategy for the order aggregator

**Status:** accepted
**Date:** 2026-09-23

## Context

Once the router splits an order into N independent messages travelling on
three separate queues, those messages can arrive out of order, at
different speeds, or — if a worker is down — never arrive at all. The
aggregator has to reconstruct "this order is done" from that scattered,
unreliable stream, without holding an order open forever and without
double-counting a message that RabbitMQ redelivers after a late ack. None
of this had an obviously single correct answer: the interesting choices
were what to key state by, whether the timeout measures from order start
or from last activity, and what a "partial" result should actually tell
the caller.

## Decision

Every item message carries the original `orderId` as both `orderId` and
`correlationId`, plus `totalItems`, unchanged by any worker. The
aggregator keeps an in-memory dict, `in_flight`, keyed by `orderId`; each
entry holds a `results` dict keyed by `itemIndex`, a `totalItems` count,
and a `lastActivity` timestamp. `aggregate_result` writes a result only if
its `itemIndex` is not already present, then updates `lastActivity`
regardless — the write and the length check happen under a single lock, so
two orders' state can never interleave. When `len(results) == totalItems`,
a "complete" message is built and published after the lock is released.
A background thread (`sweep_timeouts`) runs every second and, for any
order whose `lastActivity` is more than `IDLE_TIMEOUT_SECONDS` (5s here,
matching the test harness) in the past, publishes a "partial" message
listing every `itemIndex` not in `results` as `missingItemIndexes`, then
drops the order from `in_flight`.

## Alternatives considered

I considered a fixed deadline measured from when the order was first seen,
rather than an idle timeout that resets on every result. A fixed deadline
is simpler to reason about, but it breaks under exactly the case the
assignment calls out: a legitimately large order (50 items) whose workers
are all healthy but still working would get cut off mid-flight just
because it takes longer in aggregate, even though nothing has actually
gone wrong. An idle timeout only fires when the order has genuinely gone
quiet, which is the actual failure mode we're trying to detect. I also
considered deduplicating by relying on RabbitMQ's own delivery
guarantees (e.g. manual ack + a consumer-side idempotency check against a
persistent store) instead of tracking `itemIndex` in memory, but that adds
an external dependency for a problem a plain dict already solves at this
scale — the redelivery case only needs "have I seen this key before," not
a full exactly-once framework.

## Consequences

Keying by `orderId` → `itemIndex` makes duplicates and concurrency correct
by construction rather than by careful bookkeeping, which is easier to
convince myself is right and easier to extend. The real cost is that all
aggregation state lives in one process's memory: if the aggregator
container restarts mid-order, every in-flight order silently loses its
partial progress — there's no persistence, so a restart is effectively "N
orders quietly incomplete forever" rather than a clean partial or a clean
retry. At ten times the traffic, the single global `lock` around every
read/write to `in_flight` would become the actual bottleneck, since every
result for every order serializes through it; sharding the lock (or the
dict) by `orderId` hash would be the first thing I'd change. With a
500-item order, nothing in the logic breaks, but the `itemResults` list
embedded directly in the completion message would make that one message
large enough to be worth paginating or storing separately rather than
inlining.
