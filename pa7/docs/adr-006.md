# ADR-006 — Run the checkout saga on Temporal

**Status:** accepted
**Date:** 2026-11-08

## Context

In PA6 the orchestrator was the only place that knew where a saga was. `handleCheckout` wrote an `in_progress` record to `idempotency-store.json` before the first call, and kept the list of completed steps in a local `completed` array in memory. Only a normal finish or a thrown exception cleaned that up.

I killed `pa6-orchestrator` while shipping was slow. «FILL: what was left in `pa6/orchestrator/data/` (which record, which state), and what the same request with the same key returned afterwards. Based on the code I expect `in_progress` and 409 `idempotency_conflict` forever, but write what you actually saw.» Payment and inventory had already been done, nothing knew about them, and nothing would ever undo them.

Making this work on Temporal also forced decisions I did not face in PA6: which failures may be retried (a declined payment will decline again; a missing answer may not), and what the workflow sandbox refuses. «FILL: anything the sandbox or tsc rejected for you.»

## Decision

The workflow `checkout` in `workflows/checkout.ts` holds the saga logic: the four steps in sequence, compensation in reverse order, and the trace. It never does I/O. Each of the six HTTP calls is an activity in `activities/index.ts`, called through `proxyActivities`, with only types imported from `../activities`.

An activity decides if a failure is permanent. A 4xx throws `ApplicationFailure.nonRetryable` with the mock's own `code` as the type, so a refusal is tried once. A 5xx or no answer throws a retryable failure. The retry policy is 3 attempts, 200 ms initial interval, backoff 2, with a 2500 ms `startToCloseTimeout` (PA6's per-call budget). Without a policy Temporal retries forever. With it a stuck call fails after about 8 seconds.

The workflow reads the failure back from the `ActivityFailure`: a `TimeoutFailure` becomes `timeout`, an `ApplicationFailure` becomes its type. Every outcome is returned as a `CheckoutResult`, and the workflow never throws, so the api can map it to the same HTTP responses as PA6. Compensation is plain code after the failure: `releaseInventory`, then `refundPayment`, and only for steps that completed. Like PA6, it carries on with the remaining compensations if one fails.

The amount is still computed in whole cents inside the workflow (the same `toCents` as PA6), so it is the same on every replay.

## Alternatives considered

- **Keep the hand-rolled orchestrator and add a recovery job** that scans for `in_progress` records on startup and finishes or compensates them. I rejected it because the orchestrator would also have to persist every step's result and be sure of the order of the writes, and that is exactly the code I would be reinventing. It is a real option for a small system, but its bugs would be mine to find.
- **Retry every failure, including 4xx.** Rejected: a declined payment would be tried three times, and the test counts attempts.
- **One activity for the whole saga.** Rejected: a crash in the middle would restart the whole saga, and Temporal could not tell which step had finished.

«FILL: add a BPMN engine only if you looked at one. Otherwise leave it out.»

## Consequences

Easier: a crash no longer loses the saga. When I killed `pa7-worker` during slow shipping, «FILL: what you saw in the UI and in the logs of ports 4001 and 4003». The workflow resumed and finished, and payment was authorized once.

Shipping, however, was called twice. The call in flight when the worker died had already reached the mock, and the engine cannot know that. Activities run at least once, never exactly once. If `authorizePayment` had been the step that ran twice, the customer could have been charged twice. To make that safe the payment service would have to deduplicate on `orderId`, or accept an idempotency key.

Harder:
- The workflow code must be deterministic. I cannot call `fetch` or read `process.env` there.
- Deploying a changed workflow while others are running can break replay of those histories, so changes need versioning.
- There is more to run and watch: the Temporal server, the worker, the UI and its history store, none of which PA6 needed.
- A permanently failing call is now slower to fail. A timeout costs about 8 seconds instead of 2.5.

## What the engine took over

- Timeouts: PA6 wrapped every call in an `AbortController` and `setTimeout` inside `callDownstream` and turned the abort into `"timeout"` by hand. Now the activity's `startToCloseTimeout` does it, and the workflow sees a `TimeoutFailure`.
- Retries: PA6 had no retry loop. Now the retry policy on `proxyActivities` retries temporary failures, and `nonRetryable` marks the permanent ones.
- The in-progress record: PA6 wrote `in_progress` to `idempotency-store.json` and could leave it behind after a crash. Now the workflow history in Temporal is the record of the saga's state.
- Knowing which steps had completed: PA6 kept the `completed` array in memory, so it was lost on a crash. Now Temporal replays the recorded results and continues from the step the workflow was on.
- Idempotency: PA6's check-and-claim code, request hash and replay logic (`payloadHash`, `persistAndRespond`) have no counterpart in my code. The api starts the workflow with the Idempotency-Key as the workflow id, and Temporal refuses a second workflow with the same id.
